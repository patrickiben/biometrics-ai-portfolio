# Shared parts of the in-browser apps

TRIALMON, the UAT tracker, the Study Lifecycle Monitor and the vaccine analysis workspace run in the visitor's browser with
Shinylive (webR). A first visit downloads about 65 MB and takes 10 to 20 seconds, so a visitor
must always be able to tell what the app is doing. Three shared pieces make sure of that:

| File | What it is |
|---|---|
| [`launch_template/index.html`](launch_template/index.html) | The page for every app, used as the Shinylive export template. The Pages build fills it from `apps/<name>/launch.json` and puts in the site's head, top bar (with the theme toggle) and footer from `_partials/` (generated by `build_pages.py`), so the page is a page of the site. |
| [`launch.js`](launch.js), [`launch.css`](launch.css) | Start R in the page, report each step and keep the app in the page's theme; the launch layout, from the site's tokens (the page links `site.css`; no color is written here). |
| [`portfolio_app.R`](portfolio_app.R) | The R pattern every app uses: a startup card, readable error cards, explained empty states, a graphics warm-up, and the site's theme (a generated copy of `assets/theme/theme.R`). |
| `../<name>/launch.json` | One per app: the launch page text and the smoke test's list of outputs to check, for example [`../trialmon/launch.json`](../trialmon/launch.json). |
| [`../../.github/pages/smoke/smoke.mjs`](../../.github/pages/smoke/smoke.mjs) | The deploy smoke test, run by the Pages workflow before anything is deployed. |

The build ([`../../.github/pages/build_site.R`](../../.github/pages/build_site.R)) stages each
app's folder with `portfolio_app.R` next to `app.R`, exports it with this template, and checks the
result. Bundled examples are synthetic; the vaccine workspace also accepts user CSVs into browser session memory.

## The launch page

The page is a page of the site: the site's top bar (Apps current, with the theme toggle),
breadcrumbs and footer, in the site's light or dark theme. The page text shows at once, before any R
loads: the title, what the app shows, links to its guide and snapshot, a "Try this" list, an
optional screenshot (`"screenshot"` in `launch.json`, files in `apps/<name>/`, with a light-theme
twin that follows the theme), the synthetic data note, and the expected first-load size and time.
Below it, the live app area has a status line with the elapsed time, and a step list that each real
signal ticks off:

1. This page and its instructions.
2. The service worker is registered and controls the page (it lets R serve the app inside the
   page). The app starts only once it does, so the R download is not fetched twice.
3. R and the app's packages: `shinylive.js` loads, R's startup banner arrives from the webR
   worker (R itself has downloaded and started), then the viewer gives the app frame its address
   (the packages have loaded and `app.R` has run).
4. The app's page, served by R: the frame's `load` event.
5. The first results: inside the same-origin frame, `shiny:connected`, `shiny:busy` and
   `shiny:idle`, and the outputs themselves ("3 of 12 panels filled").

After that the status line says Ready, or Working while R recomputes. It reports instead of going
blank when: the browser has no service worker or the registration fails; the page is not under the
service worker's control, or the viewer throws "ServiceWorker controller was not found" (the page
reloads once; a second failure within two minutes shows the problem instead of looping); a file R
needs does not download (it says which, from webR's messages or a check of the app's files,
including the ones webR loads on demand, and marks step 3 as failed when that happened before the
app's page loaded); `app.R` stops with an R error (it shows R's message); the connection to R is
lost; nothing is ready after 60 seconds of visible time, or 120 seconds once R has started (a first
visit on a slow connection spends most of its time loading the packages), or the first results
have not arrived 45 seconds after the app's page loaded (it says which step it is on and why that
step usually stalls, and if one of the app's files then gets no answer within 20 seconds, it names
that file); or one update keeps R busy for 45 seconds. Each problem has a Reload button (Keep
waiting comes first while the start may still finish), links to the guide and the read-only
snapshot, and technical details for a bug report; the clock stops at a hard failure.
`window.launchStatus` and `data-state` on `#app` expose the same state to tests. Full screen covers
the page: what is behind the app leaves the tab order, and a copy of the top bar's theme toggle sits
in the app's bar. The app follows the page's theme: its own
page reads the saved `bp-theme` choice when it loads, and `launch.js` sets `data-bs-theme` on it
whenever the site's toggle or the system setting changes the page, so its plots redraw in the new
theme.

## The R pattern (`portfolio_app.R`)

```r
suppressPackageStartupMessages({ library(shiny); library(bslib); library(DT); library(ggplot2) })
source(if (file.exists("portfolio_app.R")) "portfolio_app.R" else "../../apps/_shared/portfolio_app.R")
warm_up_graphics()   # before the UI: in the browser, loads the plot fonts while the launch page reports

ui <- page_sidebar(..., app_status_ui("the KPIs, the test table and the gate"), ...)

server <- function(input, output, session) {
  output$plot <- renderPlot(guard("the area plot", { ... }))
  output$tbl <- renderDT({
    d <- filtered()
    explain_empty(nrow(d) > 0, "No tests match these filters. Clear a filter to see all 29.")
    datatable(d)
  })
}
```

- `app_status_ui(computing)` shows a startup card that names what R is computing and counts the
  panels as they fill. It stays until every visible panel has content (a DataTable counts once it
  shows rows or its own empty message) or, once R is idle, for at most 5 seconds more, so a table
  that is still drawing never sits blank without a status; the launch page's status line waits the
  same way and recounts as each value arrives. It turns on Shiny's busy indicators for every later
  update, says so when the first results take more than 45 seconds or the connection to R is lost,
  and styles errors: a panel that fails shows "Could not compute:" with the panel's name, R's
  message and "This is a bug in the app".
- `guard(what, expr)` adds what was being computed to an error's message. `req()` and `validate()`
  pass through.
- `explain_empty(ok, message)` and `empty_state(message)`: an output a visitor can see is never
  silently empty. Use them instead of a bare `req()`, which leaves the panel blank.
- `warm_up_graphics()` draws one throwaway plot in the browser only. webR downloads the graphics
  library and fonts the first time anything is plotted; without the warm-up that happened after
  the layout was drawn, so a failed download left every plot empty with no message.
- The site's look, from `assets/theme/tokens.css`: `build_pages.py` writes `assets/theme/theme.R`
  and the same code into the generated region at the top of this file, so an app needs no other
  file. `bp_theme()` is Bootstrap 5.3 precompiled (a custom bslib theme would compile Sass in the
  browser at every start); `bp_theme_head()`, which `app_status_ui()` includes, picks the theme as
  the site does (a saved `bp-theme`, then the system setting, then dark), follows later changes,
  reports it to R as `input$bp_theme` and carries the tokens as CSS variables (`--surface`,
  `--ink`, ...), the tones (`--tone-red-fg`, `-bg`, `-line`, `-fill`, `-tile`) and the shared
  component rules. `bp_theme_toggle()` is the site's light and dark button for a standalone run; it
  hides inside the launch page, whose top bar has the toggle. In R, `bp_palette(input$bp_theme)`
  gives plot colors (`$tone$red[["fill"]]`) and `bp_ggplot_theme()` the chart ink. An app maps its
  own levels onto tones (RED to red, watch to blue); `build_pages.py --check` fails on a tone below
  its contrast floor and on any color literal in an app's source. `portfolio_theme()` and
  `portfolio_colors(dark)` remain as short names for `bp_theme()` and `bp_palette()`.

## `launch.json`

`source` (the app folder), `title`, `summary` (one paragraph), `try` (three to five steps),
`screenshot` (`null`, or `src`, an optional light-theme twin `src_light`, `alt`, `width`, `height`,
`caption`), `links` (`t`, the kind of link the chip's glyph shows: `open`, `guide` or `snapshot`;
`label`; and `href` relative to `apps/<name>/`), `first_load` (`download_mb`, `first_s`,
`revisit_s`), and `smoke`:
`timeout_s`, `outputs` (ids that must have content on first load), `expect` (exact text for some
of them), `fit` (optional: a CSS selector and a window width at which that element must fit its box
without sideways scrolling, for example a table at phone width), `tabs` (a tab label and the
outputs it must fill once clicked; `"theme": true` repeats the theme check on that tab, for its
plots) and, optionally, `interactions`: named step lists done with real mouse and keyboard events
in the app, in order, on the same page, each with expectations, for example the UAT tracker's
"Try this" step as a visitor would follow it

```json
{"name": "Try this, as written: double-click DEF-04's Status, type Closed, press Enter",
 "steps": [{"dblclick": "#defects tbody tr:nth-child(4) td:nth-child(3) .uat-pill"},
           {"type": "Closed"}, {"key": "Enter"}],
 "expect": [{"text": ["#defects tbody tr:nth-child(4) td:nth-child(3)", "Closed"]},
            {"text": ["#v_def", "2"]}],
 "after": [{"dblclick": "#defects tbody tr:nth-child(4) td:nth-child(3) .uat-pill"},
           {"type": "Open"}, {"key": "Enter"}]}
```

Steps are `click`, `dblclick`, `focus` (CSS selectors in the app's page), `key`, `type` and `wait`
(ms); a click, a key and a wait are each followed by waiting for R to finish what they started.
Expectations are `visible`, `text` (a selector and its exact text), `attr` (a selector, an
attribute and its exact value), `style` (a selector, a computed style property and a regular
expression, for example a focus ring), `inViewport` and `focused` (the focused element matches the
selector). `viewport` (optional) sets the window size for that interaction only; `after` cleans up.
The lifecycle monitor's interactions tab onto its what-if sliders (no value may change; the focused
track is a named slider with its value and a ring on the handle) and then move one with an arrow
key; TRIALMON's moves along its tab strip with an arrow key and expects a 2 px focus outline.

## The smoke test

```sh
npm ci --prefix .github/pages/smoke
Rscript .github/pages/build_site.R ../portfolio-site
CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  node .github/pages/smoke/smoke.mjs ../portfolio-site --shots ../smoke-shots
```

It serves the build under `/biometrics-ai-portfolio/` as Pages does, opens each launch page with a
fresh browser profile and fails unless the page text paints within 3 seconds inside the site's
top bar, the app reaches Ready within `timeout_s`, every listed output has content and no panel
shows an error, each element listed in `fit` fits its box at its window width, the app shows the
page's theme and R has it (`input$bp_theme`), the top bar's toggle switches the app's page and R to
the other theme and back (R idle again within 30 seconds, every listed plot drawn again, no
error), the controls carry the site's accent in both themes (every checked radio and checkbox
filled with `--accent`, a slider handle with a visible border, nothing in bslib's compiled default
blue), each listed tab fills in, each listed interaction ends with its expectations met and leaves
no panel in an error, the launch page then reports no problem and no failed panel with R idle,
nothing the visit asked the site for answered 404 (webR would otherwise fetch a missing package from
elsewhere and still start), the page logged no uncaught error and no console error about one of
the site's files, and a reload reaches Ready again. The Pages workflow runs it on the build before
anything is deployed; its runs are listed under
[Actions, Pages](https://github.com/patrickiben/biometrics-ai-portfolio/actions/workflows/pages.yml).
`--fault 'REGEX=404'` (or `drop`, `hang`) with
`--expect-problem KIND` checks an error state instead, for example
`--fault 'shinylive-sw\.js$=404' --expect-problem sw-failed`.

site's bar (macOS, headless Chrome 155, served from the same machine): in two runs of the smoke
test all three apps passed, ready 6.7 s (TRIALMON), 7.0 to 7.2 s (UAT tracker) and 7.7 to 7.9 s
(lifecycle monitor) after opening on a first visit and 6.2 to 7.1 s on a reload, page text painted
in 68 to 120 ms, about 65 MB served on a first visit. 24 more first visits (each app at 1280 and
390 px, light and dark, on two builds) were ready in 6.6 to 7.9 s, with no serious or critical
axe-core 4.14.0 violation on the launch page or in the app, and six with a saved theme opposite to
the system setting opened in the saved theme. Before these changes the same machine read 6.7 to
7.9 s. Four error states were re-run on
the new launch page (a service worker script, `app.json`, `R.wasm` and `shinylive.js` that answer
404), and each was reported as such. Earlier on 2026-10-25 the other error states were checked the
same way: a font, font cache, graphics library or webR worker that does not download, an `app.R`
