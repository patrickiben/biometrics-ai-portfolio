Trial‑Management Validation Harness

Ten gates for a clinical‑biometrics deliverable, run against this repository's own SAS/R TLF pseudocode libraries and synthetic ADaM data. Most checks are structural (inventories, pattern scans, counts); G1 re-runs the synthetic study; G9 recomputes the sandbox's PK, bioequivalence and adverse-event results with separately written code; G10 reports what the harness catches when defects are planted on purpose; G5 is a manual record, not computed; G6 checks that every QTc change figure uses one reference-line convention (0, 30 and 60 ms, the ICH E14 categorical thresholds); G7 stays “not signed” until a named statistician signs for AI use; SAS is never executed (no license). No gate has a human sign-off yet. Full spec →

    What the harness catches

    A seeded-defect check (G10). Realistic programming defects from a list fixed in advance are planted one at a time in a throwaway copy of this repository. After each one the copy's outputs are regenerated, so G1's byte-for-byte check cannot fire; then the other gates and the module tests run, and the result is compared with an unmutated copy run the same way. Caught lists the layers that failed. Survived means no layer failed. Equivalent means no layer failed and no output or printed result differed (shown by diff, not assumed). The diff runs on the shipped data only, so Equivalent is not proof that a change has no effect: a change that matters only for data the sandbox does not contain is filed Equivalent. The list is hand-picked, so the counts describe this list only: they are not a detection rate and carry no interval. Survivors are reported as what the harness misses, not hidden.

(G2 has since been changed to check, program by program, the R programs that compute geometric statistics or fit a BE or dose-proportionality model, found by content (28 today, with a committed floor of 28, so a program that leaves the set turns G2 red), and each one's SAS twin: in every branch, a geometric mean must be missing or exactly exp() of a log-scale mean (10^ in R or 10** in SAS for log10 logs), directly or through a name assigned that way, a geometric CV must come from a log-scale variance in the same way, and model responses must be log-derived, so a formula built from a string fails.     Tools built: QC-process engineering adapted from the teeth check and method-invariance grid in my consilience-engine software. It measures the harness itself and is not a statistical method. The Hy's Law grid in the TRIALMON console is a structured sensitivity analysis of SAP conventions. Synthetic data; SAS not executed.

    Prior art first. Mutation testing (DeMillo, Lipton and Sayward, “Hints on test data selection,” Computer 11(4):34–41, 1978) and error seeding (Mills, “On the Statistical Validation of Computer Programs,” IBM Federal Systems Division, 1972) plant known faults to measure a test suite; the R package muttest (0.3.0, CRAN, July 2026) does this for R code. Zheng (JSM Proceedings 2019) models the errors that independent dual programming misses with a Poisson process, a model rather than an experiment. Two PharmaSUG papers by Sunil Gupta and Tomás Sabat Stofsel ask how clinical data validation should be done: “Does SDTM Validation Really Require Double Programming?” (PharmaSUG 2025, MM-227) weighs technology-based alternatives to double programming and sponsor oversight of CRO deliverables, and “Ready for Next Level SDTMs and ADaMs Compliance with End-to-End Processing?” (PharmaSUG 2026, DS-111) describes metadata-driven compliance checking. Neither abstract describes planting defects to measure what a QC process catches. The grid follows multiverse analysis (Steegen et al., Perspectives on Psychological Science 11(5):702–712, 2016) and specification curves (Simonsohn, Simmons and Nelson, Nature Human Behaviour 4:1208–1214, 2020), in the spirit of ICH E9(R1) sensitivity analyses and FDA's July 2009 DILI guidance. What is new here is no new statistics: it is measuring which defects this clinical QC harness catches against a list registered before the run (a literature search for this build found no published example, which does not show there is none), and making each potential Hy's Law flag's dependence on SAP conventions explicit.
